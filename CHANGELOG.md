- approve / approve-pair / approve-exemption-pair crash with unhandled FileNotFoundError on a missing or already-promoted .draft (1.2.1) (#102)
- a target with no staged draft beside it is refused by one line naming the draft and `ligature draft`, at exit 1, in every promote verb instead of a Python traceback (1.2.1) (#102)
- #102: every promotion verb reads `<target>.draft`, and all three read it without checking it was there. `approve`, `approve-pair` and `approve-exemption-pair` therefore answered a missing draft with a ~15-frame `FileNotFoundError` traceback at exit 1 -- nothing on stdout, and a message naming `<target>.json.draft`, a file the caller was never told about. Three states reach it, and the date-creusot pilot (recorded as `date-ligature-101`, mirrored from full-ligature-port chainlink #106) reported all three against 1.2.0 and 1.1.1, so it is not a recent regression: a target nobody drafted, a target whose draft the promotion that created it already consumed (the ordinary idempotency question -- re-running an `approve`), and a record hand-written straight to its target path. What makes it a defect rather than a design choice is the control in the same release and the same tree: `promote-evidence evidence/E-99.json` already refused the identical condition with `error: no staged draft at evidence/E-99.json.draft -- run ... first`, and `validate-work-package`, `accept-promotion` and `gate-g14` each have their own one-line version of it. It also hid the real mistake: "No such file or directory" on a file the caller was never asked about reads as a corrupt installation rather than as "you passed the target where a draft belongs", and since `approve` is a human checkpoint, a 15-frame traceback with no sentence is the one output an agent cannot relay. The fix is one fail-closed preflight, `review_checkpoint.require_staged_drafts()`, opened by all three promotion paths -- `approve()`, `approve_pair()` and `auto_promote_if_mechanical()` -- so there is no per-command guard to drift and no verb that can reintroduce the traceback behind it: `error: nothing was promoted: no staged draft at <target>.draft -- this command promotes an already-staged draft and never writes content itself: stage one with \`ligature draft <stage> <template> <target>\` (\`ligature draft --help\` lists every template), or copy the target itself to <target>.draft`. One line on stderr, nothing on stdout, exit 1 through pipeline's documented `PipelineError` fold (#83), and the `no staged draft at` opening is deliberately the one `promote_evidence` already writes. The paired verbs are stated for what they are: they promote all-or-none, so the refusal says `promotes all 2 drafts as one transaction` and names **every draft that is absent** in the same line rather than stopping at the first, while a sibling draft that *is* staged is left byte-for-byte alone for the retry -- naming a present draft would read as "restage this", which is not what the operator needs to do. A missing draft is deliberately NOT folded into `ApprovalRefused`: that means "there was a draft and the validator rejected it", and collapsing the two would tell an author with a broken artifact to go stage one. The pairing is `strict=True`, so a caller passing more drafts than targets fails loudly instead of skipping the surplus -- a preflight that passes because it did not look is the same shape as the validation default that used to mean `skip`. No refusal writes anything and none appends to `ci/results/review_log.jsonl`: the audit trail records review events, and a refused promotion is not one. The `<target>.draft` spelling is now `review_checkpoint.draft_path_for()` rather than being open-coded in five places, which is how the preflight ended up on one promote verb and not the other two. Covered by `MissingStagedDraftTest` in `tests/test_pipeline.py` (the pilot's four rows, the exact line for each verb, both paired verbs naming both drafts, a pair with one draft staged promoting neither and keeping the staged one, no audit entry, and the control that staging the draft the message names does promote it at exit 0), `MissingStagedDraftPreflightTest` in `tests/test_review_checkpoint.py` (the library-level guard on all three paths, the consumed-draft re-approval, and a G2+-failing draft still reported as `ApprovalRefused`), and `test_a_missing_staged_draft_is_one_line_through_the_packaged_binary` in `tests/test_zipapp_out_of_checkout.py` -- the pilot's surface, end to end through the shipped zipapp. Documented in `docs/cli-contract.md` §5, which is also where #108's "same crash shape, not fixed here" note now points here instead.
- write-set-check reports a file written into protected_roots as 'write set: clean' (1.2.1) (#103)
- #103: `protected_roots` was an **accounted-for** category, not an enforced one, so the half of the write set the installed skill's authority boundary 5 calls binding -- "never write into `protected_roots`" -- was the half nothing checked. A file inside a protected root needed no declaration, because the pattern matching it *was* the declaration, and two of #77's own location carve-outs made that near-universal exactly where the pipeline writes: any file under `ci/` (a canonical pipeline location) and any file under a declared crate's `specs/` tree passed for free. The date-creusot pilot planted three files inside its own ten declared `protected_roots` -- `ci/manifest/PROBE.json` and two spec-tree probes -- and `write-set-check` reported `write set: clean`, `violations: []`, exit 0, **output byte-identical to the no-probe baseline**, in three consecutive releases (1.1.0, 1.2.0, 1.2.1; reproduced again on 1.2.1 from full-ligature-port chainlink #90/#104). An agent or human using that command as evidence of boundary-5 compliance got a false all-clear: it could not distinguish "stayed inside the write set" from "wrote a new normative interaction spec into the protected specs tree". A file inside a `protected_roots` pattern is now a **violation** unless a declaration vouches for **that file**. **(1) Two classes, reported separately, because only one is a boundary-5 breach.** Each `write_set.violations[]` entry carries a `kind`, each text line is labelled `violation [<class>]`, and `details` counts the classes: `out-of-set` (written where no root permits at all), `protected-write` (written inside a protected root, blocking, exit 1, one high-severity `write-set` finding in `check --json` -- so the gate a run is judged on fails on it and not only the dedicated command), and `declaration` (a write-set shape that enforces nothing, #77's vacuous cases). `allowed_roots` now explicitly wins an overlap: a path the descriptor permits is never also a protected write. **(2) The vouch set is declarations, not locations.** A protected file is accounted for when it is product-managed in the ownership manifest, a declared user-owned document, the ownership manifest itself (it records the managed set, so it cannot vouch for its own path out of it -- without that one clause an initialized workspace would read red), or **a pipeline artifact**: a file the pipeline's own artifact system recognizes, by the same discriminators `status` uses -- the artifact kind's identity field (`boundary_id`, `interaction_id`, `report_id`, ...) or, for a work-package manifest, the `work_package` / `definition_of_done` keys that separate it from the ownership manifest sharing its directory. Shape, not schema validity: whether a recognized artifact is well-formed is another command's finding, and this check is about provenance. Recognition and the directory list come from `project_state` (`_discover_artifact_files`, `_ARTIFACT_KINDS`, and a new `artifact_dirs()`), never a second hand-kept list of "which paths the pipeline writes" that could drift from the artifact system and re-open this hole the moment a kind is added -- and `ArtifactDirectoryConsistencyTest` asserts the new registry and that discovery name the same directories in **both** directions, since a directory one knows and the other does not is precisely the drift that would reopen #103. `<target>.json.draft` inside an artifact directory is also accounted for: `review_checkpoint.stage_draft` (reached through `ligature draft`) is the pipeline's own command writing inside a protected tree, and the staged file is inert until `approve` promotes it. **One honest limit, named rather than hidden.** A protected file in a location the pipeline writes *nothing* into -- a project's own `Cargo.toml`, `.github/`, `scripts/`, `rust-toolchain.toml`, `build.rs`, `tests/harnesses/`, `docs/*-schema.json` -- still cannot be attributed: nothing in a workspace separates the project's file from an agent's, and failing closed on it would leave every mature workspace permanently red, which is how a check gets ignored. Those stay in `protected_unvouched`, non-blocking, but the audit is now **complete** (no carve-out hides any of them, which is what made the pilot's probes invisible) and `details` states in words that the verdict does not cover them, so `clean` can no longer be read as "boundary 5 holds everywhere". A file *nested below* an artifact directory is audited rather than called a violation, because the artifact discriminators disagree about depth (`_discover_artifact_files` reads one level deep; `validate_interaction.find_interaction_files` walks any depth deliberately, so a nested placement surfaces as its own G1b violation) and its provenance is not decidable in one place. **(3) `clean` is now distinguishable from "found nothing to check"** -- the report's third suggestion. `write-set-check --json` carries a `protected_surface` array reporting **every** declared `protected_roots` pattern with how many files it covered, how many are violations, and how many are unattributed; the text form prints one line per pattern and names a pattern matching no file at all as such (`protected_root (matched no file): ...`), because a protected root nothing matches protects nothing on disk and is not a surface that was checked. The skill's authority region, all ten stage prompts, both schemas' descriptions, `docs/cli-contract.md` §8/§10 and `docs/mode-p-cli-flow.md` §3 now say the protected half is enforced and name the audit-only residual; every spec-tree prompt previously told the agent that `write-set-check` reports only files *outside* `allowed_roots`, i.e. the half that was never the defect. Covered by `ProtectedWriteTest` (the issue's three probes as `protected-write` violations, `check` failing on them, `status` reporting them, the two classes distinguishable, a real spec artifact / work-package manifest / staged draft still accounted for, `{}` and a stray `NOTES.txt` in a spec dir both caught, the draft exemption not extending to other directories, `allowed_roots` winning an overlap, and the ownership manifest vouching for itself), `ProtectedSurfaceReportTest` (every pattern reported, a no-match pattern named as such, per-pattern counts, and the clean verdict stating what it does not cover), `ArtifactDirectoryConsistencyTest` in `tests/test_project_state.py`, two prompt-template assertions in `tests/test_prompt_templates.py`, and one end-to-end assertion in `tests/test_zipapp_out_of_checkout.py` (the packaged artifact, run under `python3 -I` with no source tree, rejecting the `ci/manifest/PROBE.json` probe).

- verifier_policy is closed; per-cluster overrides move under `clusters`, whose keys must be cluster names (1.2.1) (#104)
- #104: `verifier_policy` was the descriptor's only object that accepted unknown keys -- `additionalProperties: {$ref: verifier}`, so the whole rule was "any key name, as long as its value is one of creusot|verus|kani". Two consequences, both still reproducible on the shipped 1.2.0 and 1.2.1 binaries: `{"default": "creusot", "defualt": "kani"}` validated at `present-valid` with `check` exiting 0 and `findings: []`, and a `fallback` key that **1.1.1 rejected** had regressed to accepted. Chainlink #76 fixed the same reported defect (#75 upstream) by DOCUMENTING the key set while deliberately leaving the object open, because per-cluster overrides were arbitrary sibling keys of `default` and closing it would have broken gate g9's `policy.get(cluster, policy["default"])` lookup -- and documenting an open object does not constrain it: neither a misspelling nor a key naming no cluster could fail. #76's own mitigation was observability (the `status --json` echo showing the typo under `clusters` as an override for a cluster named `defualt`), which could only make a *valid* descriptor legible; it could never make an invalid one fail. **The object is closed now** -- `additionalProperties: false`, exactly `default` (required), `clusters`, `supporting` -- and the per-cluster overrides it could not be closed around moved under `clusters`, one level down, where a key is either a cluster name or a typo of one. `gate_g9.owning_verifier_by_bridge()` resolves `policy.get("clusters", {}).get(cluster, policy["default"])` and `project_state.build_project_state()` reads the declared `clusters` object instead of re-deriving it as "every key that is not default or supporting" -- which is what let the typo reach the echo in the first place. `clusters` is the one open object left in the descriptor, and it is open because its keys ARE cluster names, which no schema can enumerate; what it does is refuse a key that could not name a cluster in any artifact, via a `propertyNames` constraint carrying the same `^[a-z0-9]+(?:-[a-z0-9]+)*$` pattern `docs/closure-profile-schema.json` and `schemas/project-state.schema.json` already require of a cluster, so `{"clusters": {"Crypto_Mixed": "kani"}}` is rejected at load instead of waiting forever to be read. A key that could name a cluster the workspace has not declared yet still validates -- a project declares its clusters before it drafts their profiles -- and `clusters` is optional, so `default` alone remains the common case. **Every failure is now a named diagnostic**, and two are strictly better than before: `defualt` reads `unexpected property 'defualt'; permitted: clusters, default, supporting; did you mean 'default'?`, and the pilot's second probe `verifier_policy.closure_kind` -- which while the object was open was accepted as a KEY and failed only on its VALUE, reporting `'deductive' is not one of ['kani','creusot','verus']` and naming neither the field the pilot wanted nor the fact that the key was wrong -- is now rejected as a key and answered `did you mean '$.closure_kind' (a property of $, not of $.verifier_policy)?` by #106's near-miss machinery. One new branch in `_diagnostic_line()` was needed for the failure mode this introduces: jsonschema reports a `propertyNames` violation against the CONTAINING object with the offending key as its "instance", so the raw line read `$.verifier_policy.clusters: 'Crypto_Mixed' does not match ...` -- naming a path the user never wrote and hiding which key inside it was wrong; it now reads `$.verifier_policy.clusters.Crypto_Mixed: 'Crypto_Mixed' is not a name this object accepts for a key; permitted: a name matching ^[a-z0-9]+(?:-[a-z0-9]+)*$`. **One honest cost.** A descriptor written by 1.1.x-1.2.x that declared a per-cluster override as a sibling of `default` (`"scheduling": "kani"`, which the shipped greenfield example itself did) no longer validates; the operator moves it under `clusters`. That is the point of the fix -- that key is indistinguishable from a typo, and no documentation separates them -- but the descriptor is user-owned, so `migrate` will not rewrite it (chainlink #78's rule for normative user-owned documents still holds) and the recovery path is the load-time diagnostic, which names both the rejected key and the permitted set. `init` ships the new shape, and a workspace that never declared an override is unaffected. Deliberately unchanged: `supporting` still accepts only an array of enum members (so the #76 Defect-3 fake-write `supporting: "kani"` stays rejected), the three-value verifier domain and its case-sensitive exact-match rule are as #76 documented them, and `status --json`'s echo keeps its `default`/`clusters`/`supporting` shape and stays null for a present-but-invalid descriptor -- which now includes the typo, so the echo no longer reports an effective policy for a policy the tool just refused. Covered by new regression tests in `tests/test_project_descriptor_schema.py` (the object is closed, `defualt` and `fallback` are refused, a flat override key is refused, a non-cluster-name key under `clusters` is refused while a merely-undeclared cluster name is not, `default` is still required, the near-miss fires on `defualt`, and no suggestion is ever pointed into the open `clusters` map), `tests/test_gate_g9.py` (a cluster named `supporting` now resolves normally instead of being skipped as unresolvable -- the collision that forced #76's workaround is gone -- plus a per-cluster override still beating `default` and a policy with no `clusters` still resolving), `tests/test_project_state.py` (the echo reads the declared map, an absent `clusters` is `{}`, and the typo is `present-invalid` with no effective policy rather than `present-valid` with a bogus one), and `tests/test_zipapp_out_of_checkout.py` (all of it end-to-end through the packaged binary). Documented in `plan.md` §1.1 and `docs/mode-p-cli-flow.md` §4.
- R1 has no severity rung between error and the intra-concept info for a cross-concept call absent from I (1.2.1) (#107)
- gate-r1-g16 reports an undeclared cross-concept call into a value-domain predicate instead of blocking on it, so resolving a possible-dispatch call site no longer degrades the gate (#107)
- #107: R1's disposition table had no rung between `error` and the intra-concept `info`, so resolving a call site could only ever make the gate worse. The date-creusot pilot (mirrored from full-ligature-port chainlink #91) resolved six `possible-dispatch` call sites -- `gate-g14` went exit 1 -> exit 0 and `check --json` lost its `human_decision_required` condition -- and `gate-r1-g16` immediately went the other way, blocking on five `absent from I` edges whose callees are `Year::ok`, `Month::ok` and `Year::is_leap`: one-line domain predicates over the caller's own value. The route back was closed by design. The only place an interaction can live is `<crate_dir>/specs/_interactions/`, a `protected_root` the installed skill's authority boundary 5 forbids an agent to write; an interaction is normative, so it needs `approve`, a `ratified` `record-ruling` and `accept-promotion`, all human checkpoints (boundary 2); and with no severity below `error`, a resolved cross-concept call is checked against I or it is an error, full stop. So resolving the risk made the call graph strictly more informative and the exit codes strictly worse, and the only correct next step was one no agent could take -- reproduced end to end on fresh scratch copies, re-verified on 1.2.0 and on 1.2.1, with the five edges named in the gate output. **(1) One severity below `error`, computed rather than asserted.** A `definite-direct-call` now records `callee_shape` in `docs/callsite-schema.json`, computed by `scripts/extract_c_static.py` from the CALLEE's own body: `value-domain-inquiry` only for a `-> bool` method whose body is a closed expression over its own fields, parameters, `let` bindings and constants -- no call, no macro invocation (whose expansion is not in the token stream at all), no assignment, no index, no loop, no `unsafe`/`async`/`extern` -- so the answer is a fact about the value and the edge cannot carry a boundary; `general` for everything else, including a callee the extractor never located. The grammar is closed on purpose, in the direction that matters: a construct nobody thought of is `general`, which is the blocking half. R1 reports a cross-concept call absent from I into a value-domain inquiry at `warn` -- printed in its own `WARN:` section before the pass line, deliberately **not** counted toward `checked` (so `all discovered call sites resolved (11 discovered, 6 checked against I)` reads the same as before), carried by `check --json` as a non-blocking `medium` finding, and cleared by declaring the interaction, which remains the honest remedy. A `general` or absent shape still blocks, and an absent one now says so and names the remedy (`re-run ligature extract-c-static`), so a report written before the classification existed is not silently misread as clean. **(2) The claim is re-derived before any gate sees it.** A hand-edited `callee_shape: value-domain-inquiry` would otherwise be the one way to ask R1 not to block without declaring the interaction, so `scripts/validate_callsites.py`'s G1b recomputes the shape from the crate's own sources and rejects disagreement in BOTH directions -- an understated `general` invents a blocker the source does not justify, exactly as an overstated `unresolved` count does -- the same "computed, never stored-and-trusted" discipline `callsite_coverage` already carried, which matters because `load_reports` (the only path into the gate) admits nothing with an error-severity finding. `callee_shape_evidence.syntax_hash` pins the claim to the exact callee body it was computed from, so an edge whose callee later grew a call stops being relaxed without anyone re-deciding anything, and a claim that cannot be re-derived at all (crate sources unreadable) is rejected as unverifiable rather than trusted. The residual the grammar cannot see is named rather than hidden: arithmetic can still panic the way any arithmetic can, and a `static` read is indistinguishable from a `const` read without name resolution -- both properties of the value's domain, not of the edge. (The other two walls of that dead end were closed earlier: 1.2.0 gave an interaction a worker-reachable `draft` path, and the operator's approval checkpoints are what the runbook already relies on; this is the third wall, the one that made the gate unsatisfiable.) Covered by `CalleeShapeTest` and `ShapeInReportTest` in `tests/test_extract_c_static.py` (the pilot's three predicate bodies, and every construct that stops the grammar: call, macro, mutation, field assignment, indexing, loop, closure, unknown identifier, non-`bool` return, `unsafe`, `async`), `CalleeShapeRecomputationTest` in `tests/test_validate_callsites.py` (the re-derived claim accepted, a fabricated relaxation rejected, an understated one rejected, a stale pin rejected, an unpinned claim rejected by the schema, a claim about a method the crate does not define rejected, an unverifiable claim rejected, a report with no claim left valid, and a fabricated claim never reaching the gate), and `UndeclaredCrossConceptRungTest` + `ConsolidatedVisibilityTest` in `tests/test_gate_r1_g16.py` (warn exits 0 and is printed, `general` and unclassified still block, a relax without its pin does not relax, a warn is never counted as checked, declaring the interaction clears it, the consolidated report carries it at non-blocking `medium`). - #112: `bridge_logic` had two rules that nothing checked before a bridge was promoted, and neither of which the template producing the field mentioned. `premises` entries must be predicate applications (`scripts/bridge_harness.py`: no operators, literals, quantifiers or negation) and `bindings` keys must be snake_case, because a binding becomes a harness parameter name -- and both were reachable only through G9's compile step. The swisstable-verus pilot (mirrored from full-ligature-port chainlink #113) met both through the tool's own template: `prompts/stage-3-bridge-drafting.md` documented `premises` only as `"<premise expression>"` and said nothing at all about `bindings`, and six bridges went `draft` -> `approve` -> `validate-bridge` at exit 0 with premises reading `self.capacity() >= GROUP_WIDTH` and bindings named `GROUP_WIDTH`, then failed `gate-g9` against a review block a human had already signed. A rule no pre-approval gate checks is not a drafting slip; it is a rule the artifact was allowed to be wrong about. Both rules are now enforced by `validate_bridge.check_bridge_logic_fragments()` as a G1b check in `validate_draft_data()` and `validate_data()`, so `draft` refuses the artifact instead of staging it, `approve` refuses it instead of writing a review block onto it, and `validate-bridge` names the reason. The check is not a second implementation of the compiler: it calls `bridge_harness.compile_bridge_logic()`, the verifier-INDEPENDENT front half of `compile_bridge()` (extracted here for exactly this purpose, and returning the parsed `BridgeLogic` the renderers consume), so the fragment enforced at approve time and the fragment G9 compiles are the same code with one verdict per artifact rather than one per verifier -- a JSON Schema `pattern` or a hand-rolled premise scanner would have been a second copy free to drift, which is how an artifact G9 will certainly reject gets approved. `docs/bridge-schema.json` documents both rules in prose on `bindings`/`premises` and names the gate, and `prompts/stage-3-bridge-drafting.md` now states them up front in section 3, restates the accepted grammar, works the `&&`-inside-one-premise trap the pilot's shape implies (`premises` is a list and the list IS the conjunction, so two assumptions are two entries), and names `GROUP_WIDTH` as the counterexample. Rendering a harness, dispatching it and recording the verdict remain G9's.
