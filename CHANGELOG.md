- #114: #103 made `protected_roots` blocking, and that is the right default -- but it left a protected write that is genuinely **sanctioned** with only two routes, both worse than the defect they work around: widen `allowed_roots`, which deletes the boundary the write is supposed to live inside, or hand-edit a file outside every tool, which `write-set-check` cannot tell apart from an intrusion. The swisstable-verus pilot measured the first dead end directly (#113: a normative user-owned document that is a `protected_root`, whose only supported fix was a hand-edit no agent could make -- 14 boundaries, 15 interactions, 6 bridges and 1 conflict resolution all approved at exit 0, then the whole set refused at `accept-promotion`), and #107 hit the other end (an interaction spec whose only home is a `protected_root` an agent may not write). `ligature authorize-write --issue N --path P --op K --issuer <name> [--ttl S] [--one-shot] [--note T]` is the third route: a **tool-mediated, issue-scoped capability record**, appended to `ci/results/protected-writes.jsonl`, which only `write-set-check` consumes. **(1) The record binds, and every binding is recomputed on read** rather than trusted from its own field (the discipline #112 applied to a bridge's `callee_shape`): the exact path or an explicitly bounded pattern, the operation (`write`|`delete`), the issue, `issued_at`/`expires_at`, the one-shot flag, the named issuer, a `grant_id` that is a hash of exactly those fields, and audit metadata. A grant therefore cannot widen `allowed_roots` (`authorize-write` refuses a path no `protected_roots` pattern covers, refuses one `allowed_roots` already permits, and the ledger is consulted on the protected branch only, so a hand-appended line cannot excuse an out-of-set write either), cannot authorize another operation (`op` is a closed vocabulary and only `write` is consumable by a file walk -- a `delete` grant can never make an existing file clean), cannot outlive its TTL (the reader recomputes `expires_at == issued_at + ttl_seconds` and rechecks that `ttl_seconds` is inside `[1, 86400]`, so neither an edited nor a hand-appended record buys standing authority; an expired grant authorizes nothing and is reported as `expired`, not dropped), cannot cover another issue or path (it is scoped to one issue, which is why `write-set-check`, `status` and `check` all take `--issue N` -- with no `--issue`, no grant is consulted and the verdict is exactly the pre-#114 one), and cannot be edited in place into something else (moving the authorization to another path under a preserved id is rejected as `edited in place`). Re-issuing an identical grant is refused as a replay, so a retry of the issuing command is idempotent rather than a way to stack grants; a repeated id in a hand-edited ledger is reported `duplicate` and the last entry wins. **(2) The issuer is a named identity, never prose.** `--issuer` is required with no default; `--issuer-kind human` (the default) is a human checkpoint on the same terms as `approve`/`accept-policy`/`record-ruling` (the installed skill now says an agent must never run it), and `--issuer-kind supervisor` -- the automation lane for a recurring sanctioned write -- additionally requires the identity to appear in the descriptor's explicit `write_set.authorized_supervisors`, which `write-set-check` re-verifies *every time it honors a record*, so withdrawing the identity stops the grant on the next run and a hand-written record naming an undeclared supervisor authorizes nothing. `--note` is recorded and deliberately excluded from the grant id: no prose field is consulted when deciding whether a grant authorizes a write, and it cannot invalidate a real record either. Every refusal is one line and writes nothing: an absolute, `..`-escaping, directory or vacuously-bounded path, `--one-shot` on a pattern, a TTL outside `[1, 86400]`, a replayed grant, and a ledger that itself sits inside a declared protected root -- a workspace whose protected roots cover `ci/results/` is told so rather than handed a capability trail whose every append is a boundary breach. **(3) An authorized write is reported, not excused.** It is clean *and* leaves `authorized_writes[]` in `write-set-check --json` with its grant id, issue, operation, issuer, issuer-kind, expiry and status (`active`, or `spent` for a one-shot grant whose file is present), counts under its pattern's `protected_surface[].authorized`, and is named in `details` -- so a `clean` verdict over a protected root a grant was used on can never read as "nothing was written there". The ledger is carried in `grants[]` either way, with every record's status (`active`/`expired`/`other-issue`/`unverified-issuer`/`duplicate`/`no-issue-named`) and every line that claims to be a grant and is not usable with the reason, including a ledger that cannot be read at all (which yields no grant rather than an unproven one). The trust model is stated rather than glossed: the ledger is an audit trail, not a signature, the same model `review_log.jsonl` and `human_rulings.jsonl` already use -- what it forecloses is a promoted-by-default protected write, and what #114 adds over it is the recomputation, so an existing entry cannot be edited into a different authorization.
