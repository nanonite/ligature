### Fixed
- every command that loads the project descriptor crashed with an unhandled FileNotFoundError traceback when the root had no project-descriptor.json (1.2.1) (#108)
- extract-c-static, validate and 13 other commands report a missing project-descriptor.json as one line naming the file and `ligature init`, at exit 1, instead of a Python traceback (1.2.1) (#108)
- #108: `load_project_descriptor` read `project-descriptor.json` without checking that it existed, so in a root that was never `init`-ialised every command going through that loader and then using the descriptor unconditionally died with a ~12-frame `FileNotFoundError` traceback at exit 1 -- nothing on stdout, no mention of `init`, and the absolute path of the installed zipapp in the frames. The swisstable-verus pilot (mirrored from full-ligature-port chainlink #107) hit it through `extract-c-static --target x86_64-unknown-linux-gnu`, the first command a worker reaches for in a pilot that is not initialized yet (that pilot's `init` is chainlink #27), so the only signal available to anyone following the worker contract was a traceback: recorded as `swisstable-verus-mcp-007` in `swisstable-verus/findings/limitations.jsonl` with the full transcript beside it. **This was not "every command behaves this way"** -- `status` printed `descriptor: absent (project-descriptor.json)` at exit 0, `check` reported `invalid_input` at exit 5, `doctor` exited 0, and `migrate --upgrade` said `workspace is not initialized; run \`ligature init --mode <mode>\` first`; `extract-c-static` and `validate` crashed, which is what made it a defect rather than a design choice. Fifteen commands crashed that way, verified against the pre-fix tree rather than inferred: `validate`, `extract-c-static`, `check-bridges`, `gate-g9`, `gate-g14`, `gate-g18`, `gate-g19`, `gate-g20`, `generate-feature-ledger`, `generate-contact-sheet`, `measure-gold-set`, `select-pilot-cluster`, `draft`, `approve`, `promote-evidence`. The fix is one guard in the one function all of them share, `project_descriptor.read_descriptor_text()`, so there is no per-command wording to drift and no command can reintroduce the traceback behind it: `error: cannot read project descriptor <path>: no such file -- run \`ligature init --mode <mode>\` to create one, or pass --descriptor <path> to name a descriptor that exists`, one line on stderr, nothing on stdout, exit 1 through pipeline's documented `PipelineError` fold (#83) and exit 2 from the standalone CLIs -- matching `validate-promotion`'s existing unreadable-descriptor handling and `docs/exit-code-contract.md`'s invalid-input code, whose full reach into `pipeline.main()` is the drift that document leaves to #56/#57/#58. The message keeps the `cannot read project descriptor <path>: ...` family chainlink #83 established for exactly this failure, so the surfaces that wrap a call site in their own prefix and the ones that print `error: {e}` still say the same thing -- `measure_gold_set`'s and `validate_promotion_receipt`'s own prefixes are dropped, since the guard's message already names the file, and two call sites printing `cannot read project descriptor: cannot read project descriptor <path>` for one missing file would have reintroduced the drift the guard exists to remove. A missing file, a directory and undecodable bytes are three distinct conditions with three distinct lines, so a `--descriptor` naming a directory is never answered with advice to run `init`. The commands that report an absent descriptor as data -- `status`, `check`, `write-set-check`, `doctor` -- are untouched, because they never needed the file and therefore never had the crash. Covered by `UninitializedWorkspaceTest` in `tests/test_pipeline.py` (all fifteen commands asserted to the exact line, the `migrate` parity the pilot compared against, the `status`/`check`/`doctor` surfaces that must keep reporting the condition as data, and a `--descriptor` that names its own bad path) and `MissingDescriptorTest` in `tests/test_project_descriptor_schema.py`. Related, not fixed here: #106 is the same crash *shape* on a different input (a missing `<target>.draft` sibling for `approve`/`approve-pair`/`approve-exemption-pair`); the pre-flight there belongs to those commands, not to the descriptor loader. Documented in `docs/cli-contract.md` §8.
- bridge_logic: predicate-application-only premises and snake_case bindings are stated in the template and enforced before approval, not only by G9 after a human has signed (#112)
- #112: `bridge_logic` had two rules that nothing checked before a bridge was promoted, and neither of which the template producing the field mentioned. `premises` entries must be predicate applications (`scripts/bridge_harness.py`: no operators, literals, quantifiers or negation) and `bindings` keys must be snake_case, because a binding becomes a harness parameter name -- and both were reachable only through G9's compile step. The swisstable-verus pilot (mirrored from full-ligature-port chainlink #113) met both through the tool's own template: `prompts/stage-3-bridge-drafting.md` documented `premises` only as `"<premise expression>"` and said nothing at all about `bindings`, and six bridges went `draft` -> `approve` -> `validate-bridge` at exit 0 with premises reading `self.capacity() >= GROUP_WIDTH` and bindings named `GROUP_WIDTH`, then failed `gate-g9` against a review block a human had already signed. A rule no pre-approval gate checks is not a drafting slip; it is a rule the artifact was allowed to be wrong about. Both rules are now enforced by `validate_bridge.check_bridge_logic_fragments()` as a G1b check in `validate_draft_data()` and `validate_data()`, so `draft` refuses the artifact instead of staging it, `approve` refuses it instead of writing a review block onto it, and `validate-bridge` names the reason. The check is not a second implementation of the compiler: it calls `bridge_harness.compile_bridge_logic()`, the verifier-INDEPENDENT front half of `compile_bridge()` (extracted here for exactly this purpose, and returning the parsed `BridgeLogic` the renderers consume), so the fragment enforced at approve time and the fragment G9 compiles are the same code with one verdict per artifact rather than one per verifier -- a JSON Schema `pattern` or a hand-rolled premise scanner would have been a second copy free to drift, which is how an artifact G9 will certainly reject gets approved. `docs/bridge-schema.json` documents both rules in prose on `bindings`/`premises` and names the gate, and `prompts/stage-3-bridge-drafting.md` now states them up front in section 3, restates the accepted grammar, works the `&&`-inside-one-premise trap the pilot's shape implies (`premises` is a list and the list IS the conjunction, so two assumptions are two entries), and names `GROUP_WIDTH` as the counterexample. Rendering a harness, dispatching it and recording the verdict remain G9's. The one deliberate consequence, asserted rather than left implicit: a bridge outside the fragment is not a valid bridge specification, so `gate_g14.load_bridges()` -- whose contract is "every FULLY valid bridge, not just present" -- excludes it and G9 reports "no promoted bridge discovered" at `EXIT_BLOCKED` instead of naming it; that is the treatment every other pre-approval rule already got there (a conclusion-mismatched bridge never reached G9 either), and the reason survives in the pre-approval gate where an author can act on it. Covered by `CompilableFragmentTest` in `tests/test_validate_bridge.py` (the pilot's exact `==`, `<`, `+`, `>=`, `&&` and `GROUP_WIDTH` shapes, a nested non-snake_case sub-binding, the same compiler's undeclared-root and unavailable-obligation rules, the draft path, and the verifier-independence control), `UncompilableBridgeIsRefusedBeforePromotionTest` in `tests/test_gate_g9.py` (the cross-command agreement invariant: one command refuses it, the other cannot pass it), and `SimulatedBridgeOutputTest.test_a_model_that_misses_the_fragment_rules_is_refused_at_draft` plus two template tests in `tests/test_prompt_templates.py`.

### Fixed
- doctor ignores the global --descriptor flag and reports the default project-descriptor.json instead (1.2.0) (#109)
- #109: `ligature doctor` was the one command that accepted the global `--descriptor` flag and ignored it -- it resolved the descriptor from `ci/manifest/installation.json`'s own `descriptor_path`, so `ligature --descriptor <invalid>.json doctor` printed `user-owned project-descriptor.json  schema: valid` and exited **0**, a clean verdict about a file it never opened, while `status`, `check` and `write-set-check` all failed closed on that same file. The pilot's own probe (`/tmp/opencode/probe-closure-kind.json`, a copy of the initialized `swisstable-verus` descriptor with `closure_kind: "full"`) drew the disagreement in one line: `status` -> `descriptor: present-invalid`, `check --json` -> exit 5 with `conditions: [blocking_findings, gate_integrity_failed, invalid_input]`, `write-set-check` -> exit 2 with `write_set.state: unknown`, `doctor` -> exit 0. A CI pre-flight that validated a candidate descriptor with `doctor` -- the natural command for "is my descriptor OK?" -- passed a descriptor `check --json` rejected three lines later: a false negative on a validation gate, not a crash. `doctor` now validates the descriptor `--descriptor` names, resolved exactly as the other commands resolve it (as given: absolute, or relative to the cwd, and not required to be inside the workspace -- confining it to the workspace would have made it disagree with them again), and reports it as its own `descriptor in force: <path>  schema: <state>` line above the inventory; the gate reads that descriptor, so an invalid, absent, or unreadable one exits **2** per docs/exit-code-contract.md's invalid-input precedence, exactly as the installed descriptor's own states already did under #74. The inventory is deliberately unchanged: `--descriptor` selects the descriptor doctor *validates*, never the one `init` installed, so a `user-owned` line for the installed descriptor and a gate line for a candidate stay two statements about two files rather than one silently standing in for the other -- dropping the installed line would have made `doctor --descriptor <candidate>` silently stop reporting an installed file. Two boundaries the fix deliberately does not cross: naming the installed descriptor is *not* an override (the manifest's workspace-relative path and the flag's absolute one are compared after `resolve()`, so `--descriptor <workspace>/project-descriptor.json doctor` is byte-identical to plain `doctor`), and a flag that was never supplied is not an override either -- `main()` now records `descriptor_supplied` before it fills in the workspace default, so a never-initialized workspace still reports `installation: not-initialized` and exits 0 instead of failing closed on a descriptor file it never had. `migrate` keeps recovering the descriptor the manifest recorded and is never handed the flag: it recovers what `init` installed, not what a caller is trialling. `inspect()` takes the flag as an optional keyword (`None` = not supplied) and `DescriptorInForce` carries the override's path, schema state, and the installed path it displaced, with the gate reached through one `InstallReport.descriptor_gate` property so it can never be evaluated against a file the operator did not ask about. Covered by 15 new regression tests in `tests/test_ligature_install.py` (`DoctorDescriptorFlagTest`): the pilot's exact enum-invalid probe outside the workspace exiting 2, the four-command agreement invariant (`doctor` 2 / `status` `present-invalid` 0 / `check` 5 / `write-set-check` 2) over one flag, the installed descriptor still reported valid, valid/absent/non-JSON/workspace-relative overrides, the `docs/..` spelling proven not to be an override, both uninitialized-workspace directions, `migrate` unaffected, and a before/after workspace snapshot proving the gate writes nothing. Documented in `docs/cli-contract.md` §1/§8/§10 and `docs/implementation-inventory.json`.

## [1.1.0] - 2026-09-29

### Fixed
- #86: `gate-g14` accepted `generic_callees_type_universal_or_creusot_owned: true` from a closure profile with nothing checked (date-ligature-043, mirrored from full-ligature-port-workspace chainlink #85; Stage 8C): the condition was printed as a non-blocking info note -- "a HUMAN DECLARATION this gate cannot verify … It is not a checked condition, and is reported every run so it never reads as one" -- so a profile could declare `generic_callees=true` and the cluster would pass without any actual verification, and a FALSE declaration was silently accepted, the probe that confirmed the note being unable to distinguish an honest declaration from a fabricated one. The obstacle itself is real (CG3, plan.md §3: which callees are generic is type information no artifact in this pipeline carries), but it was treated as permanently uncheckable when the closure's own records settle it in the common case.
