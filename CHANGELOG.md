## [1.1.0] - 2026-09-29

### Fixed
- #86: `gate-g14` accepted `generic_callees_type_universal_or_creusot_owned: true` from a closure profile with nothing checked (date-ligature-043, mirrored from full-ligature-port-workspace chainlink #85; Stage 8C): the condition was printed as a non-blocking info note -- "a HUMAN DECLARATION this gate cannot verify … It is not a checked condition, and is reported every run so it never reads as one" -- so a profile could declare `generic_callees=true` and the cluster would pass without any actual verification, and a FALSE declaration was silently accepted, the probe that confirmed the note being unable to distinguish an honest declaration from a fabricated one. The obstacle itself is real (CG3, plan.md §3: which callees are generic is type information no artifact in this pipeline carries), but it was treated as permanently uncheckable when the closure's own records settle it in the common case. Both remedies the issue offered are implemented. **(1) Verified from artifact data**: new `gate_g14.generic_callees_verification()` computes the condition whenever every work package in the closure has a recorded achievement and none of those achievements is a Kani result -- CG3's gap is Kani's alone (plan.md §4's own table: a creusot/verus result is universal over type parameters the way Kani's per-monomorphization result is not), so with no per-monomorphization assurance anywhere in the closure no generic callee it rests on is Kani-owned. The gate now reports `VERIFIED from artifact data` every run instead of the HUMAN DECLARATION note, and the bit joins the recomputed set: a profile declaring `false` over such a closure is a mis-declared condition, rejected by `check_declared_conditions` in the same two-direction check as every other computed condition and never excusable by a degradation record. The claim is stated relative to the closure -- the per-cluster scope g14 has always certified, never a pipeline-wide one. **(2) A gap with a tracking record when the records do not determine it** (a Kani result anywhere; a work package whose report is missing, unreadable or empty): the condition stays out of the computed set, so an honest declaration is never refuted by silence, and `gate_cluster` emits an error tagged with the condition -- beside a degradation record naming it (`ceiling: per-instantiation`, `capability_gap: CG3`, a tracking issue, plan.md §3's own response to every capability gap) the cluster is reported *degraded* under that ceiling with the record in the output, explicitly a declared and tracked gap; without one the declaration would be accepted unverified, so the cluster stays BLOCKED. G17 in `validate_closure` gains exactly the exception that makes such a record expressible at all: naming this condition beside a `true` declaration is no longer the "stale excuse" hard error, because profile and record alone cannot tell an unverifiable declaration from a closed gap -- while staleness for that key moves to where the evidence lives, with `gate-g14` rejecting a record still naming the condition once the closure's records verify it, as an untagged error no degradation record can excuse (the same discipline that keeps mis-declared bits unexcusable). Covered by new regression tests in `tests/test_gate_g14.py` (`DeclaredConditionTest`: verified-from-artifact-data on the all-deductive fixture, the issue's own `true`-over-a-Kani-only-closure reproduction blocking, the same declaration beside a tracking record degrading with its ceiling and issue in the output, an unrecorded work package forcing the gap, the pre-existing excusable false-declaration path preserved where it belongs, and the stale tracking record), and `tests/test_validate_closure.py` (the CG3 tracking record validates clean while every other condition keeps the stale-excuse rule). Documented in plan.md §4/§8.5/§12, `docs/closure-profile-schema.json`, `docs/degradation-record-schema.json`, `docs/implementation-inventory.json`, and `scripts/select_pilot_cluster.py`'s architectural note (selection-time use of the declaration is unchanged: a cluster nobody has picked has no closure records to compute from).
- #85: the closure profile's `closure_kind` enum had no partially-verified option (date-ligature-041, mirrored from full-ligature-port-workspace chainlink #84): `docs/closure-profile-schema.json` accepted only `deductive` and `bounded`, so `validate-closure` rejected `partial`, `mixed` and `degraded` at G1a with `'…' is not one of ['deductive', 'bounded']` -- a pilot that cannot achieve full deductive closure (date-creusot, Stage 8C) had no way to declare its actual state, its only options being to round the claim up to `deductive` (over-claiming universality it never established) or down to `bounded` (claiming a uniform guarantee over a closure that does not deliver one uniformly). The enum gains exactly one value, `partial` (plan.md §4): partially verified -- part of the closure carries the guarantee its evidence supports and part does not. One value, not three: `degraded` already names gate g14's own outcome for a cluster released under a degradation record (a status orthogonal to whichever kind the profile declares), and the evidence-composition fact `mixed` would name is already carried by `conditions.single_verifier_system` and the closure's own evidence kinds -- a closed vocabulary holding three synonyms for one state is the free-text wobble §4's G17 discipline exists to refuse. `partial` claims strictly less than either uniform kind, so `gate_g14.check_closure_kind` deliberately gains no branch for it: evidence kinds can refute `deductive` (a Kani result anywhere in the closure) and under-claim `bounded` (an all-deductive closure), but cannot speak to partiality at all -- that is a coverage question, and its answer is already emitted by the findings that own it (a missing achieved record blocks whatever the kind says, no degradation record can excuse an absence of evidence, and a failing closure condition still needs its own degradation record). The value is accepted everywhere the vocabulary appears, so declaring it cannot be rejected one layer up or crash a generated projection: #73's descriptor intent field, both `status --json` echoes in `schemas/project-state.schema.json` (`descriptor.closure_kind` and the per-cluster `closure_kind`), and the feature ledger's projection in `docs/feature-ledger-schema.json`. Covered by new regression tests in `tests/test_validate_closure.py` (G1a accepts `partial`; the vocabulary stays closed to `proved`), `tests/test_gate_g14.py` (a `partial` profile is reported with the outcome and `check_closure_kind` never refutes it from evidence kinds), `tests/test_project_descriptor_schema.py`, `tests/test_project_state_schema.py`, `tests/test_project_state.py`, and `tests/test_generate_feature_ledger.py`. Documented in plan.md §1/§4, `docs/mode-p-cli-flow.md` §4, and the schema descriptions themselves.

- #83: `validate-work-package` and `validate-promotion` died on a bad path argument with a raw Python traceback (date-ligature-030, found by the date-creusot pilot at Stage 7 / Stage 4.5): `validate-work-package /tmp/nonexistent-wp.json`, `validate-promotion /tmp/nonexistent-promo.json` and `validate-work-package /tmp` all exited 1 but printed `FileNotFoundError`/`IsADirectoryError` straight out of `pathlib` -- fail-closed in substance, but an error surface that named neither the offending argument nor what the command expected. Both path-taking validators read their argument through the same shape of code, so it is one defect and the fix is one shared guard, `scripts/manifest_input.py`: `ensure_manifest_path()` pre-flights the CLI's positional argument *before* the workspace's project descriptor or any flag checks (so the message names the argument the user actually got wrong, not whatever the workspace happens to lack next), and `read_manifest_text()` performs the same checks immediately before the read for library callers, both raising `ManifestInputError`. Every CLI surface prints that message as one line -- `error: manifest not found: <path>`, `error: receipt not found: <path>`, `error: <kind> path is a directory, expected a file: <path>` -- and still exits 1: pipeline `main()` now catches it alongside `PipelineError`, and each validator's own `main()` handles it directly, so no path reaches the user as a stack trace (a library caller sees the exception propagate rather than a `Finding`, since there is no artifact to have an opinion about yet). The same defect class on the same commands is closed too: a `--workspace` with no `project-descriptor.json` used to traceback out of `load_project_descriptor()` (now `error: cannot read project descriptor <path>: ...`; exit 1 through pipeline's documented `PipelineError` fold, exit 2 from the standalone CLI, matching `validate-promotion`'s existing unreadable-descriptor handling and docs/exit-code-contract.md's invalid-input row), and a standalone `--descriptor` naming a missing path or a directory likewise. `ManifestInputError` is deliberately *not* an `OSError` subclass, so callers' existing `except OSError` blocks cannot swallow it and blame a bad manifest on the descriptor instead. Covered by new regression tests: `StandaloneBadPathTest` in `tests/test_validate_work_package.py`, two new cases in `StandaloneCliMainTest` in `tests/test_validate_promotion_receipt.py`, and four new cases across `CmdValidatePromotionIntegrationTest`/`CmdValidateWorkPackageIntegrationTest` in `tests/test_pipeline.py` (each asserting the exact one-line message, exit 1, and no `Traceback` anywhere), plus `tests/test_manifest_input.py` for the guard's own contract. Documented in `docs/cli-contract.md` §2 and `docs/implementation-inventory.json` (runtime module `scripts/manifest_input.py`, test file `tests/test_manifest_input.py`).
- #82: `accept-promotion` had no review-provenance guard, so it minted a Stage 4.5 receipt over review blocks nobody had approved. It required only a non-empty `--reviewer` string, then deterministically computed `artifact_manifest` (real file hashes), `promotion_id`, `schema_versions` and `policy_version` and validated the assembled receipt against `validate-promotion`'s own checks -- but `validate_promotion_receipt.validate_data()` checks hashes, containment and cross-references, never where a `review` block came from, and a hand-written `{"reviewer": ..., "reviewed_at": ...}` is byte-identical on disk to one `review_checkpoint.approve()` wrote. So every accepted artifact's review block stood on its own authority: the date-creusot pilot could run the command over all 24 promoted artifacts -- including the eight boundary/interaction specs whose review blocks an unattended agent wrote and a human ruled unauthorized (pilot #14, date-ligature-031) -- and nothing between the artifact and the receipt ever asked how those blocks got there. The guard added here is a review-provenance check at the last gate before the write transaction: every accepted artifact that carries a non-empty `review` block must have a matching approval entry in the workspace's append-only `ci/results/review_log.jsonl`, the trail `review_checkpoint.approve()`/`approve_pair()`/`auto_promote_if_mechanical()` write and the only record that a review event happened through the sanctioned path (`review_checkpoint.review_provenance_gaps()`, reading it back). Matching is by the artifact's resolved path plus the block's own `reviewer`/`reviewed_at` (with the documented mechanical-carry-forward exception), and a missing, unreadable or damaged log is a refusal, not a pass -- fail-closed, no default, no cwd-relative path, same lesson `accept_promotion()` already learned about `REVIEW_LOG_DEFAULT`. Artifacts with no review block (the reliance policy, evidence records, concept specs -- schemas that declare none) have nothing to prove, and a refusal names the offending artifacts and appends nothing. Round 2 (reviewer of this fix): the provenance guard as first delivered still did not stop the issue's own reproduction -- run against a copy of the real date-creusot pilot workspace with the issue's exact command, `accept-promotion` exited 0 over all 24 artifacts, because those eight contested review blocks DO have audit entries (the unattended agent ran `approve --reviewer chainlink-reviewer` itself, and provenance cannot tell that run from a human's) while the fifteen evidence records carry no `review` block at all, so provenance is silent about both. The issue's second stated remedy is therefore implemented too: a **human-ruling gate**. Every artifact in the receipt's manifest must additionally carry a `ratified` human ruling over that exact version of the file, in the new append-only `ci/results/human_rulings.jsonl`, recorded by the new `ligature record-ruling --reviewer <name> --verdict ratified|rejected --artifact <path> [--artifact <path> ...]` command (docs/cli-contract.md §1/§5/§10, `cmd_record_ruling`/`record_ruling`/`ruling_gaps`). Ruling hashes are computed by the same `compute_artifact_manifest()` the receipt uses (same containment, alias and witness-promotion-digest rules), so ratify-then-edit invalidates the ruling until it is re-recorded; a `rejected` verdict, a missing ruling over any one artifact, a ruling over an older version, an unrecognized verdict, and an unreadable/damaged log are all refusals that name the artifact and the command to fix it, and the gate runs *after* the provenance check so a genuinely unprovenanced review block is still reported for what it is rather than as bookkeeping. `record-ruling` itself refuses an empty `--reviewer`, an unknown verdict and a malformed `--ruled-at`, and fails closed without a loadable project descriptor. This is what makes the pilot README's own constraint -- "#14's accept-promotion must not run before rulings 1 and 2 land" -- mechanically true instead of prose, and it covers what provenance structurally cannot: agent-run approvals and artifacts promoted outside any tool path. Verified against a copy of the real pilot workspace, not only temp fixtures: the issue's exact command exits 1 with no receipt while rulings are unrecorded, a recorded `rejected` ruling keeps it blocked, and a recorded `ratified` ruling over the set then lets it through.

Two supporting changes. (1) `pipeline.py`'s `approve`/`approve-pair`/`approve-exemption-pair` still defaulted their audit log to the cwd-relative `review_checkpoint.REVIEW_LOG_DEFAULT` -- the gap #45 explicitly set aside as a follow-up -- so approving an artifact in another workspace recorded the entry in whatever repo the CLI ran from; the guard and the sanctioned path would then have read two different logs and every legitimately approved artifact in an external workspace would have been refused. They now log to `<workspace>/ci/results/review_log.jsonl`. (2) #45's own directory-in-place-of-review_log repro now trips the provenance *read* first (same refusal, earlier), so the append-side rollback coverage was re-based onto failing the append's own fsync rather than left silently passing for the wrong reason. Covered by new regression tests: `ReviewProvenanceTest` in `tests/test_generate_promotion_receipt.py` (10 cases, including the defect repro and a real `approve()`-then-accept), `CmdAcceptPromotionProvenanceIntegrationTest` in `tests/test_pipeline.py` (hand-written block refused whatever `--reviewer` says; `approve` through the real CLI then `accept-promotion` accepted; review block edited after approval refused), plus the existing acceptance fixtures now recording the approval entries they were implicitly assuming. Documented in `docs/cli-contract.md` §1/§5/§10, `docs/trust-and-compatibility-boundaries.md` §5/§8, `docs/implementation-inventory.json` (43 registered commands), and the installed skill's human-checkpoint rule and command table.

- #77: `project-descriptor.json`'s `write_set` was consumed by nothing and mentioned in no generated file -- no command reported a file outside `allowed_roots` or inside `protected_roots`, the descriptor accepted every shape of the object (including `allowed_roots: ["**"]` and `protected_roots: []`, rejecting only the object's total removal), and the strings `write_set`/`allowed_roots`/`protected_roots` appeared in none of the files `init` generates (not the hash-pinned skill authority region, not any of the three prompts). The write set is the only thing the descriptor says keeps an implementation inside its crate's `src/` and `tests/` and away from the pinned upstream checkout, `ci/manifest/**` and the specs -- an unenforced boundary is indistinguishable from an undeclared one. New `scripts/write_set.py` evaluates the write set against the workspace's actual files: a file is accounted for by an allowed root, a protected root, the ownership manifest, a declared crate's `specs/` tree, a canonical pipeline location (`ci/`, `evidence/`, workspace-level `specs/_<kind>/`, `docs/witnesses/`), or the pinned upstream checkout (`port_source.repository`); everything else is an out-of-set write. `ligature write-set-check` reports the violations (plus the protected-surface audit -- files inside `protected_roots` nothing vouches for, non-blocking) and exits 0/1/2 per the exit-code contract; `status --json` carries the verdict as `write_set.state` (`clean`/`violations`/`unknown`); `check --json` carries one high-severity `write-set` finding per violation, so `check` exits 1 on the date-creusot pilot's `rust/rogue/evil.rs` repro that every v1.0 command reported nothing for. The vacuous declaration shapes (`allowed_roots: ["**"]`, `protected_roots: []`) are flagged as violations of the write set's own purpose rather than rejected by the schema -- descriptor schemas are a stable public contract, and the codebase's own precedent for exactly this situation (#67's Stage-P0 placeholder) is a conservative finding, not a schema rule. The same change closes the descriptor-level `gate_integrity` path-escape gap (companion evidence on #74): an entry resolving outside the workspace (absolute, or a `../` traversal) is now refused rather than hashed against someone else's file -- the discipline `validate_work_package.check_gate_integrity` already applies to work-package manifests. The installed skill's authority region gains a binding write-set rule and the command table gains the verb; all three prompts gain a write-set note. Covered by new regression tests in `tests/test_write_set.py`.
